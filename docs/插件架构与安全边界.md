# Seed 插件架构

## 目标

Seed Core 不硬编码插件功能，只提供稳定协议、生命周期、隔离 Host、共享组件和经过审查的本地 Broker。本分支迁移官方插件到 API v2：独立工程、轻量 Manifest、代码注册能力和插件自己的 DOM/React UI，构建为单个 main.js 并以 .seedpkg 分发。SDK、客户端与新插件尚未发布。

```text
官方源码仓库 / 社区开发者仓库
          │ 构建
          ▼
       .seedpkg ──► MotusAI Cloud 审核、发布、组织授权与对象存储
                         │ 签名发现文档 + 账号目录 + 下载摘要
                         ▼
Electron Main ──► userData/plugins/installed
      │                    │ 静态 Manifest
      │                    ▼
      │             Connector 路由/审批/Schema
      │                    │ invoke
      ▼                    ▼
受控 Broker ◄──── sandboxed-web Plugin Host（每插件独立）
      ▲                    native-host Utility Process（每插件独立）
```

## 进程边界

- Main：安装、原子切换、OAuth、安全存储、系统目录选择器、本地 Broker。
- Connector Utility Process：插件生命周期、校验后的代码注册路由、输入输出 Schema、本地 HTTP/SSE 网关与审计。
- Plugin Host：每个 `sandboxed-web` 插件使用独立隐藏 BrowserWindow，关闭 Node.js 并禁止网络、导航、窗口及系统权限；每个官方 `native-host` 插件使用独立 Utility Process，需要 Node.js 与声明范围内的主动网络连接时由该进程执行。Main 监督进程退出、清理其运行贡献并按退避重启；其他插件与 Connector 不随之退出。
- Renderer：通用产品壳，不解释插件业务；官方可信插件前端直接挂载到产品文档的普通 DOM 容器，与产品壳共享 Renderer；没有 iframe、独立 WebContentsView、坐标同步或滚动转发。浏览器统一负责布局、裁剪和滚动，共享组件从 SDK 直接导入。Renderer 关闭 Node 并使用统一 CSP；这不是逐插件前端安全沙箱。后端凭据仍由隔离服务和受控存储持有。

能力声明的 `exposure` 决定协议边界：默认的 `terminal` 能力可被连接器插件按自身协议暴露给远端 Agent，也可被 Manifest `consumes` 已显式声明依赖的其他插件发现和调用；`plugin` 能力只允许显式的插件间调用；`local` 能力只由客户端本地入口调用。Seed Core 不建立或代理远端终端连接；插件间调用始终需要消费方的 `consumes` 白名单。

Agent 工具名是跨插件共享的全局命名空间。提供方用 `agent.tool_name` 声明别名时，应采用“动作 + 明确对象”的稳定名称；工作区文件、临时附件、网页、Office 文档和 Skill 私有资源不得共用宽泛名称后再由消费方猜测路由。消费方必须在合并动态工具与自身内置工具后校验最终名称唯一性，遇到非法名称或重名直接拒绝创建 Agent 运行时，不得静默改名、覆盖或兼容旧别名。Seed Core 只传递和校验通用 annotation 结构，不维护具体工具名称清单。

## 网络与连接生命周期

插件主动联网时按目标范围声明：`network.connect.internet` 用于公网，`network.connect.lan` 用于局域网，`network.connect.loopback` 用于当前设备。禁止使用带插件或厂商业务名称的网络权限。权限表达安全边界，不让 Seed 理解 HTTP、WebSocket、TCP、MQTT 等业务协议；连接的认证、心跳、重连、消息处理和限流全部由插件负责。

官方 native-host 使用 PluginService.registerConnection 登记连接权限、传输名称与状态，并提供幂等 close。Component 卸载、重载或 Seed 退出时先中止连接，再等待清理。连接存在不计入全局任务忙碌状态；实际工作才使用 app.tasks。正常卸载不是用户取消，不得丢失持久会话和未回答提问。

`local.http-api` 仍是 Seed 统一 loopback 网关的独立权限。所有插件入站 HTTP/SSE 都向该网关注册路由，插件不得自行监听端口。`network.connect.*` 只允许主动连接；Core 只负责权限、生命周期和诊断状态，不代理流量，也不实现插件重连。

浏览器授权是另一项通用 Broker：插件按 OAuth 2.0/OIDC Authorization Code + PKCE 标准声明权限，Seed 只负责打开系统浏览器、一次性 `state`/PKCE、固定自定义协议回调与按插件隔离的取消和超时。授权码只交还发起该请求的插件；Seed Cloud 会话不会交给插件。服务商令牌、用户资料和连接行为仍归插件或其服务端。新增同标准的服务商无需为 Seed 添加插件 ID 特判。

下载代码绝不进入 Main 或 Connector 的 Node 上下文。Main 只静态读取身份、资源、翻译和权限；能力契约由隔离服务注册后校验。Connector 通过进程消息路由能力与统一 Local HTTP/SSE，不再解释 v2 表单或管理视图。UI 与服务分别加载 main.js 的入口，后端资源和 RPC 绑定实际插件身份与代次；退出后撤下贡献并独立重启。独立进程只是故障隔离，不是操作系统级沙箱。

## 安装与更新

官方与社区插件共用：

```text
<userData>/plugins/
├── installed/<plugin_id>/<version>/
├── staging/
└── development/<plugin_id>/   # 仅开发启动；完整构建目录
```

插件文件保存在上述目录；启用版本与来源状态保存在客户端 SQLite 数据库。

卸载保留插件的 `plugin-data/<plugin_id>` 私有文件、加密配置及凭据，便于重新安装后恢复。设置中的“清理插件数据”仅清理已卸载插件的这些保留的数据：先列出具体插件并确认永久删除，执行时重新核对完整安装记录。未获授权、已停用或加载失败但仍有安装记录的插件不会被视为孤立数据；外部工作区文件、备份及应用账号数据不在清理范围内。清理与安装、卸载互斥，拒绝不安全的数据根目录和插件目录符号链接，并分别报告清理成功、跳过及失败项。

安装器限制包大小、文件数、展开大小、路径、符号链接、重复路径和大小写冲突；v2 校验包摘要与 Manifest resources 摘要，再写 staging、原子切换。复用已有 SDK/Broker 的插件功能和界面变化不需要客户端业务改动；新增高权限宿主原语仍需客户端升级。

目录接口按 `platform + architecture` 返回当前设备可用版本；例如 Windows x64 的协议值是 `win32 + x64`。安装界面允许选择版本：选择更高版本执行升级，选择更低版本执行降级。客户端对每个插件只保留当前活跃版本；切换时先将原版本移入临时隔离区，SQLite 状态写入成功后永久删除，失败则恢复原版本。

客户端不内置或兜底 .seedpkg。云安装继续使用签名发现文档、账号目录、下载校验与授权；发布平台不在本轮重构范围。分类和发布账号在包外维护，不进入新 Manifest。已获授权插件之间仍按 consumes 调用；开发目录识别与热重载使用同一 v2 静态读取器及运行时，不写入正式安装数据库。生产构建不启用开发目录。

Cloud 在目录、企业图标和下载接口实时检查组织成员资格。Seed 启动时、目录变更时和运行期间定期查询已安装插件的授权；无法确认时，已确认授权的运行许可最多保留 5 分钟，超时后从 Plugin Host 与 Connector 移除插件运行时，但保留本地插件文件与配置。退出云账号也会撤销本地运行许可。重新登录并获得授权后可重新载入，无需重新安装。

## Core Broker

本地文件属于 Core Broker，而不是插件运行时。Files 插件只是能力协议适配器：

```text
files.read_file → sandboxed plugin → seed.broker.files.invoke → FileBroker
```

FileBroker 统一解析本地文件路径并执行文件访问边界；Files 无需逐目录授权，macOS/Linux 的文件系统根为 `/`，Windows 使用可用盘符根。`root_id` 用于定位文件系统根，不代表用户授予某个目录的访问权。FileBroker 继续检查敏感路径、符号链接、路径越界、冲突哈希、原子写入和产物解压安全策略，并管理备份；Terminal Token 与下载认证由各自的宿主边界处理。

需要捆绑原生可执行文件的插件在 Manifest 中声明 `sidecars` 并申请 `process.sidecar`。Core 只允许运行当前插件包内声明的 Sidecar，以参数数组启动、不经过 shell；使用用户目录作为工作目录时，FileBroker 根据 `root_id` 和相对路径解析并校验目录，不要求逐目录授权。纯计算任务可显式选择插件包工作目录并使用 `read` 访问语义，同时统一限制环境变量、输出大小、超时、取消和进程树清理。Sidecar 的平台包、命令白名单和业务能力仍由插件拥有，客户端不得识别 OfficeCLI、SenseVoice 等具体实现。

音频设备由全局受控 Host Service 管理；转写格式、模型选择和业务流程由插件拥有：

```text
Obsidian → Seed Local HTTP Gateway → Recording
Recording → seed.audio → AudioService → microphone / system audio / mix
Recording → plugin-owned WAV/transcription flow → authorized model / Cloud relay
```

Recording 插件定义录音能力、Schema 与流程，并在 Seed 的统一固定端口下注册命名空间路由。`AudioService` 负责系统权限、采集/混音、持久分段、最近一次三路 WAV 和资源清理，按所属插件返回受控音频数据。插件使用自己的加密配置或已授权 Cloud relay 转写，不存在客户端 ModelGateway 或特定模型硬编码。托管服务的原始平台凭据不交给插件。

这意味着：

- 更新 Files 的描述、方法编排或 UI Contribution，不需要更新客户端；
- 新增一种现有 Broker 可以支持的插件，不需要更新客户端；
- 新增摄像头、系统命令等新的高权限 Host Service，必须更新并审查客户端。

## 唯一运行时与数据沿用

插件只依赖公开 SDK 的 Plugin、PluginService、Component、Events 与组件，SDK 由宿主注入。宿主不再包含 apply(ctx)、能力 YAML 加载、声明式 UI 解释器或 Cordis/Cosmokit。前端和后端是同一框架下的独立实例与分离依赖图，不是两种插件协议。所有异步资源、路由和连接由 Component 生命周期管理。

已有 API v1 安装记录仅显示不兼容，不执行旧插件；安装新规范的同 ID 插件后，原加密设置、凭据键和 plugin-data 路径继续沿用。删除旧代码与删除用户数据是两件不同的事。

本地开发放入 plugins/development/<plugin_id>，或由插件 npm run dev 持续构建并同步。只有开发服务器启动的未打包客户端会启用发现和监听。目录读取经过与正式包相同的 v2 资源校验，完整产物以私有快照供运行；半写文件不进入运行时。重载先撤下旧代次、关闭所属 UI／服务与请求，再载入新代次；其他无关插件不重启。配置触发的后端重载与代码构建代次分开处理，不能因为刷新别的插件而重复重启。

开发源与正式安装源只在统一运行时入口合并。同 ID 按 SemVer 选择版本较高的本地源，同版本保留开发源以支持热更新；选中正式源时仍需满足云端授权。移除开发源后恢复满足授权的正式源；正式安装文件、版本状态和云端授权不被开发流程改写。市场只提示比当前选中源更高的版本，不提示降级。快照只留当前构建，不保留历史；普通配置和业务恢复状态仍写原来的安全存储。

## 暂缓项

- 发布者签名与可信密钥库；
- 可安装 Bundle/Profile 包；
- 插件版本回滚 UI。

这些能力暂缓不影响当前 `.seedpkg` 目录、安装、沙箱执行、官方 `native-host` 和 Broker 路由跑通。
